# Syntax highlighting

Edit colors source code and markup with a Tree-sitter layer and an independent [LSP overlay](../lsp-highlighting/spec.md). Tree-sitter highlighting and [bracket navigation](../bracket-navigation/spec.md) share the same parse for the current text and language, including embedded languages. TextKit 2 applies colors as rendering attributes and redraws existing visible fragments as soon as a highlighting layer changes. Edits track which rendering ranges need repainting. Highlighting leaves the text storage, viewport position, editing metrics, undo history, dirty state, and saved bytes intact. The native selection background leaves the syntax colors of selected glyphs visible.

- Auto Detect is the initial mode. It uses a case-insensitive exact basename match first and then the longest recognized extension. Untitled and unrecognized files display as Plain Text. Save and Save As resolve the new path in automatic mode.
- **Change Language Mode…** in Control and a right-click on the title bar file icon open the same language picker for the current document. Auto Detect appears first, Plain Text second, and the bundled languages follow alphabetically. The active choice is indicated. Select a language to override detection or select Plain Text to remove colors. Auto Detect clears the override and restores the mode for the current path.
- Manual choices follow their buffer through Save As. Edit remembers up to 100 named path overrides and restores the mode of each saved session document, including an untitled draft. An older session or an unknown mode can fall back to automatic detection.
- When switching files, keep the current buffer visible while preparing syntax for the incoming viewport on a background task. Parse from the beginning through the visible lines and a small margin within a bounded prefix. A file whose opening viewport exceeds that prefix can display immediately while syntax runs in the background. A prepared viewport keeps its colors while the full document is parsed and queried. Mode changes request syntax immediately and redraw the visible editor as results become available. For [Odin](../odin/spec.md), Ruby, Shell Script (Bash), Solidity, Swift, and Zig, retain the previous buffer tree and apply text edits to it before parsing the next revision. Share the tree with bracket navigation and allow one background parse for the buffer to run at a time. On the editing path, Zig tries to parse and query a short edited line within 2 ms for small buffers. Odin, Ruby, Bash, Solidity, and Swift try to parse and query the edited viewport within 6 ms. While a fresh result is pending, Solidity carries the previous paint ranges through the edit and extends them only across token continuations. The other incremental modes query the previous tree with edits applied to its positions and carry the previous paint ranges if the query exceeds its budget. Large buffers defer construction of a contiguous syntax snapshot and carry the previous paint on the editing path. Query the visible slice with a margin on the current tree and query a new slice when scrolling. Apply the fresh result when it arrives. For the other languages, edits schedule a background parse after 45 ms. The first letter of `error.H` has the error-tag color in the first frame. A shortened keyword such as `retur` loses its keyword color across the entire word in the first frame. A shortened error tag such as `Hell` stays colored across its entire range. When the incremental result is pending, retain valid colors over whole tokens and allow the short Zig word check to classify keywords and explicit error tags. Adding or removing a separator keeps the colors of adjacent words that still have distinct boundaries. When the fresh result changes how the text is split into tokens, replace the affected old color ranges together. Apply each new token color to its whole range in one frame. TextKit applies available captures as new fragments become visible. A canceled or outdated result cannot recolor the current document. An unavailable query leaves editable plain text. If no first result is available for 150 ms, the window shows an activity indicator. Rendering adapts to macOS appearance.

## Tokenization during editing

Tree-sitter highlighting must keep typing responsive and avoid visible flicker in every bundled language, including when LSP is disabled or unavailable. Use the active language's lexical and syntactic rules to determine token boundaries and roles, with enough context for incomplete input, multiline constructs, and injected languages. A shared implementation can use the appropriate grammar for each mode.

While the new parse is pending, carry the previous token color over its whole surviving range, including characters typed into or extending that token. A change in syntax can temporarily keep the previous color. When the result for the current text arrives, apply the new colors and ranges together in one frame, including when tokens split or join. A stable token keeps its color throughout the edit. A token whose classification changes can go directly from its old color to its new one without flashing an intermediate color or showing a mix of the old and new colors across its glyphs. Newly introduced text with no prior token classification can receive its first color when parsing completes.

For every mode, add an automated check in the isolated native editor with LSP off. Force the synchronous parse budget to expire, hold the background result, and verify that editing remains responsive and the previous color stays on the whole surviving token. Inspect the rendered glyphs in the first edited frame, while the result is pending, and on the first frame after it is applied. Exercise typing and Backspace, an edit that changes a token boundary or role, and representative language-specific tokenization. Include Unicode and embedded code where supported. A grammar capture check or a final-frame check alone does not qualify. Record the check in the [language support matrix](../../language-support.md).

## Tree-sitter and semantic tokens

Apply these rules when adding a language with semantic tokens or updating an existing Tree-sitter or LSP integration for such a language.

- Use Tree-sitter for roles the grammar can prove, including literals, comments, keywords, and structurally unambiguous declarations where the language grammar identifies them.
- Leave a range in the default text color when choosing its color requires symbol or type resolution. For example, if a language assigns different colors to identifiers used as types and values, let semantic tokens classify any identifier whose role cannot be distinguished by the grammar. Spelling conventions and typical uses of a parse position are insufficient evidence.
- Use the same theme color in both layers for a range they both classify. For the same source text, receiving semantic tokens keeps the color of syntax already painted by Tree-sitter. Verify the overlap against the supported server, including ambiguous or incomplete code. When a capture disagrees with the server, narrow or remove it or align the theme mappings.

## Bundled languages

C, C++, Clojure, CSS, Erlang, Go, HTML, JavaScript, JavaScript JSX, JSON, Lua, Markdown, Objective-C, Objective-C++, Python, Ruby, Rust, Shell Script, Solidity, Swift, TOML, TypeScript, TypeScript JSX, YAML, and Zig. JSON also recognizes comments in JSONC, Clojure covers EDN, and Zig covers ZON. Markdown uses inline and fenced-code grammars and HTML supports embedded JavaScript and CSS.

Auto Detect uses Objective-C for `.m`, Objective-C++ for `.mm`, and C++ for ambiguous `.h` headers. C++ uses the shared C-family rules for directives, keywords, types, literals, and comments, including when no language server runs. Use the language picker to select a different mode for a header.

The Zig and ZON base layer colors keywords, literals, primitive types, comments, and explicit field designators. In Zig it also colors built-in function names such as `@sizeOf`, labels, explicit error tags, named container fields, single `const` bindings with an unambiguous type expression, and parameter names with a direct primitive type annotation. The two layers use the ZLS color for these roles. In `const a: X = struct {}`, the role of `X` comes from semantic analysis. Ordinary function and call names, arbitrary field access, tuple element type names, and other unresolved identifiers get their colors from ZLS.

In Markdown, apply inline code highlighting inside table cells and color heading markers with the heading. An HTML comment in Markdown keeps its comment color from its opener through its close, or through the end of the buffer while it is unclosed. Comment-like text inside code stays code.

In Ruby, when a quoted or percent string is missing its closing delimiter, highlight its body through EOF, including subsequent lines. Complete interpolations and escapes keep their usual Ruby highlighting. A real closing delimiter ends the string, and code after it resumes normal highlighting.

In Zig and ZON, a double-quoted string gets string highlighting from the first opening quote, including while its body or closing quote is still being typed. The color of an unfinished string stops at the line break or EOF. Escapes retain their string color, and quoted identifiers retain identifier highlighting. While a full parse is pending, classify an ordinary string on the short edited line using the Zig grammar.

In Solidity and inline Yul, keep quoted text colored from the opening delimiter while typing ordinary, Unicode, and hex literals. Recover an unfinished string through its closing quote, unescaped line break, or EOF. Escaped quotes and line continuations stay in the string. Keep an unfinished block comment colored through EOF and restore the following code when the closing delimiter is entered. Keep the prefix of a hexadecimal number colored while its first digit is pending. [Solidity literal grammar](https://docs.solidity.org/en/latest/grammar.html)

## Acceptance

- Open `main.RS`, `widget.test.ts`, `widget.tsx`, `data.jsonc`, `.zshrc`, `Cargo.lock`, `Gemfile`, `library.h`, `widget.m`, `widget.mm`, `build.zig.zon`, `app.app.src`, and `deps.edn`. Check that their resolved languages and syntax colors match the file modes. In a `.mm` file check Objective-C selectors and C++ templates together.
- Select Rust on an untitled buffer, save to a different extension, and verify the manual mode follows the buffer. Select Plain Text, and then Auto Detect to restore path-based colors. Quit and reopen named and untitled drafts to check persistent choices.
- Compare a ranged Zig query against a full parse after multiple CRLF and Unicode edits. The query must return a whole token even if the requested range starts inside it. On a large Zig file, scroll to an unqueried position and verify that the editor queries the new viewport.
- Change a highlighted buffer containing Unicode and incomplete code. Undo and redo, and switch modes while highlighting runs. Verify that no obsolete syntax result overlays the document and that the caret, selections, scroll, and dirty state behave normally.
- Open a Markdown table with inline code and a heading with leading and trailing `#` markers. Check both table header and body cells, and compare the heading markers with its text. Type `<!--` above a heading and a fence and check that the comment color runs to the end. Close the comment before the heading and check that ordinary highlighting resumes. Repeat with a literal comment opener inside inline code or a fenced block.
- `./script/check` checks real captures in every bundled grammar and checks the pixels on the first frame after opening a small Rust file and a Swift file above 64 KiB. It samples the stationary viewport after opening and reopening a Swift file with a saved position beyond the preview budget, then checks color when scrolling past the prepared range. It also checks that highlighting preserves the text, selection, dirty state, and undo history, and validates Plain Text clearing and manual mode recovery.

The per-buffer tree, time budget, and viewport queries follow [Zed 1.29.3](https://github.com/zed-industries/zed/blob/d01b134cddf5e4f71964deb2d6f81cdb38fcf1e7/crates/language/src/buffer.rs#L1943-L2018).
