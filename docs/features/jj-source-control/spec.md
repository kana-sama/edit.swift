# Jujutsu sidebar

The Jujutsu sidebar brings the daily `jj log`, change editing, and repository undo workflow into Edit. Choose **Jujutsu** from the sidebar switcher or **View → Focus Jujutsu** with Shift-Command-G. Both are available when the window’s open folder belongs to a Jujutsu workspace, including a subfolder or linked workspace. The shortcut reveals the sidebar and focuses the graph. Press it again from the sidebar to focus the document with Jujutsu still visible. In other windows, Shift-Command-G runs **Find Previous**. Switching to a folder outside Jujutsu falls back to Worktree, or to Search if the window has no folder. If the workspace exists but its executable is unavailable, show the reason inside the sidebar. The existing [change indicators](../jj-change-indicators/spec.md) and [inline diff](../jj-inline-diff/spec.md) supply the file statuses and comparison behavior.

## Sidebar layout

- Put **Changes** above **Change**. Give the graph and the selected change independent scrolling and a movable horizontal divider. Graph height initially fits about five typical rows. Either section collapses to its header and yields its scroll space. Keep the graph controls reachable in the collapsed header. Preserve the section heights and collapse choices while switching sidebar modes.
- Follow the trailing section disclosure in Finder’s Favorites. In Jujutsu, place the chevron immediately after the heading so the action buttons can share the row. Keep the chevron visible and reserve the same space for both directions. The title and chevron form one button that exposes its expanded state. [Finder sidebar](https://support.apple.com/en-us/127254) · [Disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls)
- The Changes header offers the named revset picker, **Go to Working Copy**, **Operations**, and **New Change**. Show the selected name in the header. Open a compact popover with a scrollable list and a fixed code area below it. Give each row one line for the name, a checkmark for the active revset, and a pencil at the trailing edge. Truncate long names to keep the pencil reachable.
- Give each graph row exactly two lines. The first is the change subject. The second shows state icons, the short change ID, and bookmarks, with long text truncated. Distinguish the working copy, immutable changes, conflicts, and divergence with icons and semantic colors. Include the state names in accessibility labels and tooltips. Keep row selection independent of revision state. Retain merges, distinguish skipped ancestry in a filtered graph, and preserve graph position and selection when the selected change is still present.
- The Change section shows one line of description and uses the same colored ID and status icons as the graph. Display the count by **Changed Files**. Reuse [Worktree’s `SidebarFileTree`](../../../Sources/Edit/SidebarFileTree.swift) with a data source for the selected revision’s changed paths. Reuse its folder hierarchy, disclosures, row spacing, file icons, selection, keyboard navigation, and status colors. Include added, modified, deleted, renamed, copied, and conflicted paths reported by jj, including inherited conflicts. Provide the specific change type to accessibility. Show **No changed files** for an empty change.

## Browse and edit changes

- Initially preview the active revset. Hover a row or use Up and Down to update the code area, keeping the active graph checked. Keep the preview visible when the pointer moves into the code. Click a row or press Return to apply it and close the popover. Show the full expression in a selectable, scrollable monospaced editor with colors for functions, pattern kinds, operators, and quoted strings. Preserve line breaks and indentation. Default Log previews the effective `revsets.log` value. All Changes uses `all()`. [Jujutsu 0.46 revset grammar](https://raw.githubusercontent.com/jj-vcs/jj/v0.46.0/lib/src/revset.pest)
- Use the pencil to edit the name in its row and the expression in the same code area. **New Revset…** opens an inline name below the list and an empty expression. Display the editing actions beneath the code. Keep the draft visible while the pointer crosses other rows. Accept multiline expressions. Check custom expressions with jj before saving and show errors beside the editor. Names are unique within the project. Saving a new revset selects it. Editing an existing row preserves the active choice. Offer **Delete** inside the editor for custom entries. Deleting the active entry selects Default Log. Built-in entries support renaming and reordering, with their expressions available read-only.
- Drag rows to reorder them using the insertion marker. Reordering preserves the active graph. Save the list, its order, and the selected revset in Edit’s application support, keyed by the canonical Jujutsu workspace root. Opening a subfolder or reopening the project restores them. The graph loads up to 600 changes and indicates when the result was limited. Keep the last complete result while evaluating the selected revset. Show the evaluation error when the expression becomes invalid, so the picker still lets the user switch or edit it.
- Select a revision to show its details. Double-click a mutable revision to run `jj edit` and make it the working copy. For an immutable revision, offer **New Change Here** and **Cancel** in a sheet. If the revision is already `@`, keep the current workspace and buffer. **Go to Working Copy** reveals and selects `@` even when the selected revset excludes it. Keep that revset selected. External operations refresh the graph and the working-copy marker.
- **New Change** creates a child of `@`. **New Change Here** creates a child of the selected revision. Both make the child the working copy. Clicking the subject or choosing **Describe…** opens an anchored popover with Edit’s regular text editor. Give the editor a stable, scrollable viewport 72 monospaced columns wide at the default font size. Soft-wrap longer lines. Render the first 50 characters of the first line in bold and its overflow in red. Show the subject count against 50 below the editor. Save accepts longer subjects.
- For a mutable change, focus the editor and select the first line for quick renaming. **Save** and Command-Return apply the description. **Cancel** and Escape dismiss the draft. An immutable description opens in the same viewport with a **Read-only** indicator and supports selection and copying.
- Offer **Squash into Parent** in the change context menu and the selected change’s actions menu when the revision and its single parent are mutable. If both have descriptions, let the user review the combined text before applying. **Abandon Change…** identifies the affected change, descendants, bookmarks, and any working-copy switch in its confirmation sheet. Let jj determine the resulting revision state.
- Run repository mutations on the workspace associated with the selected result and reconcile the real state after the command. Use the existing document save and external-change lifecycle for affected open files. Never reuse a document buffer based on superseded file contents for subsequent writes.

## Open a changed file

- A file click opens it in the document area with all available inline diff hunks expanded. Compare the change with its parent, or with the merged parents for a merge change. Use the observed source path for a rename or copy.
- An existing text file from `@` opens as the live buffer in the ordinary editor, with the existing [inline diff](../jj-inline-diff/spec.md) controls. Showing all hunks is part of opening from the tree. Save, editing, individual gutter toggles, and Escape follow the usual document behavior.
- A file from another revision opens in a read-only view. A slim strip above its contents says **Read-only** and shows the short change ID and description. A deleted text file also uses the strip, labeled **Deleted File · Read-only**, and shows the removed lines from its baseline. An added file in the revision preview shows its inserted lines. For non-text files, use the available [read-only file preview](../file-preview/spec.md) and the file’s change status. A revision view remains tied to the version the user opened.
- Selecting another graph entry updates the Change section. The document changes when the user opens a file or when a working-copy operation updates its live version.
- For `@`, overlay the open buffer’s current status using the same comparison as Worktree. A newly changed buffer can add a row before save, and returning it to the baseline can remove that row. After disk changes, an open Jujutsu sidebar coalesces snapshots so new, removed, and changed paths appear without a terminal command. Preserve the normal [snapshot cadence](../jj-change-indicators/spec.md#working-copy-snapshots) elsewhere. Historical revisions keep their recorded file list.
- A file in mutable `@` offers **Discard File Changes…** in the outline context menu when the path can be restored. Confirm the exact affected paths. Restore those paths from the merged parent tree, including both ends of a rename, and discard unsaved edits to those paths when the operation succeeds. Leave other working files and buffers intact.

## Preview and apply Undo or Redo

- **Operations** opens an anchored popover with **Undo** and **Redo** across the top. Both open a preview of the next operation in that direction. Use actual jj history, including actions made in a terminal. Show the operation’s description, short operation ID, time, and origin when known. Align the content at the leading edge and scroll long previews while keeping the apply action visible. Keep the popover open on the selected tab after success and refresh the preview for that direction. If no further operation is available, show the reason on that tab and disable the apply action.
- Show the working-copy change before and after, followed by revisions and bookmarks that will be restored, removed, moved, or updated. Include a disclosure for the paths whose on-disk contents will change, with a label for each effect. A description-only edit can change the graph with zero paths affected. A squash can change the graph and disk paths while `@` keeps the same change ID. Indicate newly affected conflicts when determinable.
- Build the preview from the currently observed operation and the target chosen by the corresponding jj command. Use read-only repository observation. Validate the operation head and relevant working-copy state again at apply. If an external operation or pending writes change the expected effect, replace the preview and require a new confirmation. Use the existing save and conflict flow for affected unsaved buffers.
- **Undo Operation** runs `jj undo`. **Redo Operation** runs `jj redo`. Keep the text buffer’s undo shortcuts for text. Follow jj’s workspace restriction for cross-workspace operations. If Edit cannot establish a coherent preview of the command’s effects, show the reason and withhold the apply action. Reconcile displayed changes against the operation jj actually records.

## Acceptance

- Open a workspace through its root and through a nested folder. Check the Jujutsu picker title, Focus Jujutsu, and both directions of the Shift-Command-G focus toggle. Switch to a plain folder and check the disabled Jujutsu commands and restored Find Previous shortcut. Check an empty change, long subjects, a merge, a bookmarked immutable node, and a conflict. At minimum sidebar width, collapse and reopen both sections. Check that the titles and chevron slots keep their horizontal position and that adjacent actions remain visible. Exercise divider drag, independent scrolling, keyboard selection, and both system appearances.
- Preview **Default Log** and **All Changes**. Add a multiline revset and verify that the preview preserves its text and highlights the expression. Edit an inactive row, drag it to a new position, and verify that the chosen graph stays active. Delete an active custom entry from its editor. Reopen the project from its root and a subfolder and verify the restored order and selection. Open another project and check that it has its own list. Invoke **Go to Working Copy** while an expression excludes `@` and verify that the selected revset stays checked.
- With a non-`@` revision selected, verify that a different node still marks `@`. Double-click a mutable revision and an immutable one. Cancel the immutable prompt and repeat with **New Change Here**. Run a terminal operation and check that the panel follows it without moving a valid selection.
- Compare the tree’s folder disclosure, selection, file icons, and status colors with Worktree. Click added, modified, renamed, deleted, conflicted, and binary files. Confirm the correct comparison and all eligible hunks open on first display. Open a working-copy text file, edit it, and save from the ordinary editor. Check the read-only strip on a file from another revision and on a deleted file from `@`, then open a live file and check that the strip disappears. Switch the working copy with an affected open file and exercise the existing unsaved-file flow.
- At minimum sidebar width, check that a long revset name leaves the header actions reachable. Check that a long description and bookmark leave the graph at two rows of text and preserve space for the file outline. Reopen the description in editable and read-only states and verify that the editor retains its viewport. Check initial subject selection, live bold and red ranges across edits and undo, scrolling, and saving. Check that the revset editor and operation popover align content at the leading edge and fit long details.
- Type in a clean tracked file and undo the edit. Verify that the file enters and leaves the working change’s outline before any repository mutation. Write another file to disk and watch it appear. Discard its changes from the file context menu, and verify that an unrelated modification stays in the working copy.
- Preview Undo for a terminal squash. Check that the removed child reappears, the parent diff changes, and the working-copy file effects match the preview. Preview and perform Redo. Repeat with `Edit`, a description-only operation, and multiple Undo and Redo operations. Check that the selected tab stays put when the next preview loads and when that direction reaches the end of its history. Check a new head or snapshot arriving while the popover is open and a next operation owned by another workspace. Opening or dismissing the popover must not record a repository operation.
